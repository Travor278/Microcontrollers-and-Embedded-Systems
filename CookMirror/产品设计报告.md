## 二、市场分析与差异化

### 2.1 现有竞品扫描

> 调研口径:截至 2026-06-02,以家庭厨房中"选菜-备菜-烹饪-调度-安全-复盘"完整链路为对象,扫描智能屏、智能冰箱、智能厨电、料理机器人、温控锅具、厨房安全设备与菜谱内容平台。

#### 2.1.1 竞品地图:市场已有能力被分散在 8 类产品中

| 竞品类别 | 代表产品/方案 | 已解决的问题 | 关键局限 | 对 CookMirror 的启示 |
| --- | --- | --- | --- | --- |
| **家庭智能屏 / 厨房智能显示** | Amazon Echo Show 15/21、Google Nest Hub Max、小度/天猫精灵智能屏 | 大屏菜谱、语音计时、视频娱乐、家庭日历、智能家居控制 | 只是"看菜谱的屏";没有下视摄像头,无法看锅、看食材、看火候;没有锅温、燃气、火焰传感器;安全能力依赖外部设备 | CookMirror 不能只做大屏,必须把"屏 + 感知 + 安全执行"做成闭环 |
| **智能冰箱屏 / 食材管理中控** | Samsung Family Hub / AI Vision Inside、海尔智家屏、LG ThinQ 冰箱屏 | 冰箱库存识别、过期提醒、购物清单、基于库存推荐菜谱 | 位置在冰箱门,不在灶台视线中心;只能管理"做饭前",不能监督"正在做";对火候、锅温、油烟和燃气泄漏无直接感知 | CookMirror 可对接冰箱库存,但核心价值应落在"烹饪现场" |
| **智能烤箱 / 蒸烤箱 AI 摄像头** | Samsung Bespoke AI Oven、Brava Smart Oven、Tovala Smart Oven | 封闭腔体内识别食物、推荐烘烤参数、扫码启动预设程序、远程查看烤箱状态 | 场景局限在烤箱或预制/半预制食品;不能覆盖中式明火、炒锅、备菜台和多灶并行;摄像头只看腔体内部 | 可借鉴"视觉识别 + 参数推荐",但 CookMirror 应覆盖开放式灶台 |
| **温控锅具 / 智能锅具** | Hestan Cue、CHEF iQ Smart Cooker、米家智能锅具 | 精准控温、分步视频指导、压力锅/电磁炉联动、称重与预设程序 | 依赖专用锅/炉/压力锅;通常只能感知锅具自身状态,不能理解灶台整体;Hestan Cue 官方说明其 guided cooking 并不真正检测锅内发生了什么 | CookMirror 需要用红外阵列 + 视觉识别补足"真实锅内状态" |
| **多功能料理机 / 桌面烹饪机器人** | Thermomix TM7、TOKIT Omni Cook、添可食万、九阳炒菜机器人、美的 HiCooking 机型 | 自动搅拌、加热、称重、蒸煮、海量步骤菜谱,显著降低失败率 | 本质是"把人从锅前移走";封闭锅腔/专用锅体限制菜系和锅气;清洗维护成本高;占台面;不适合家庭已有灶具和锅具 | CookMirror 的定位应是"放大人的能力",不是"替代人下厨" |

| **菜谱 App / 生鲜与半成品平台** | 下厨房、豆果美食、Samsung Food、HelloFresh、Tovala Meals | 内容供给、菜谱搜索、购物清单、营养信息、半成品配送 | 手机端为主,烹饪时手脏不便;不能实时观察执行偏差;没有硬件传感和本地安全执行 | 内容可合作接入,但用户体验入口应迁移到镜面大屏和语音/手势 |

#### 2.1.2 代表性产品观察

- **智能屏很适合厨房,但停留在"显示器"层面**:Amazon Echo Show 15/21 已经证明 15-21 英寸壁挂智能屏适合厨房组织和娱乐;Google Nest Hub Max 也明确主打 hands-free recipes、多计时器、营养查询和 Quick Gestures。问题是它们无法理解锅里发生了什么,更无法关火关阀。
- **冰箱屏解决的是"食材入口",不是"烹饪现场"**:Samsung Family Hub 已经具备 AI Vision Inside、SmartThings Food、菜谱推荐和购物清单能力,但其屏幕和摄像头都围绕冰箱,只能回答"家里有什么",不能回答"锅里现在该怎么办"。
- **智能烤箱的视觉 AI 已经成熟,但场景封闭**:Samsung Bespoke AI Oven 可通过内置摄像头识别食物、优化烹饪设置并提供过火提醒;Tovala 通过条码/二维码绑定烹饪曲线;Brava 用光烹饪和分区控温提高自动化程度。这些都证明"视觉 + 烹饪参数"成立,但它们覆盖不了开放明火和中式翻炒。
- **温控锅具证明"火候数字化"有价值,但数据维度太窄**:Hestan Cue 通过锅具、炉具和 App 联动实现温度/时间自动控制;CHEF iQ 把称重、压力锅和 guided recipes 结合。但这类产品通常只看锅具自身,不看手、食材、刀工、灶台环境和燃气风险。
- **料理机/炒菜机器人降低门槛,却削弱"自己做饭"的体验**:Thermomix TM7 和 TOKIT Omni Cook 代表了全功能料理机方向,优势是步骤菜谱和自动参数;添可食万、九阳、美的等炒菜机方向则更接近"自动炒"。它们适合"不想做饭"的人,但不适合想学习、表达、陪伴、保留锅气和家庭厨房仪式感的人。
- **ROKI/方太等厨电套系最接近"厨房 OS",但封闭生态明显**:老板 ROKI 已经提出数字菜谱、AI 烹饪助理、烟灶锅联动;方太幸福家 App 集成设备控制、健康菜谱和大模型问答。这说明巨头认可"厨房系统化"方向,但用户必须进入其品牌套系,对已有厨房的改造成本高。
- **安全设备有刚需,但缺少解释性和场景智能**:Aqara 气体报警器可推送报警并联动智能阀门;FireAvert 可在烟雾报警持续时切断燃气或电源。这类产品能"最后一刻制动",但不能在油温升高、空锅干烧早期就结合菜谱语境提醒用户。

#### 2.1.4 结论:市场空白不是"AI 做饭",而是"AI 在现场教人、安全地做饭"

1. **没有直接竞品完整占位**:现有产品分别解决"看菜谱""管库存""自动烤""精准控温""自动炒""报警关阀"中的一小段,但没有产品同时具备 **壁挂镜面交互 + 开放灶台视觉 + AR 主动指导 + 红外锅温 + 多菜调度 + 燃气关阀 + 健康营养闭环**。
2. **CookMirror 的竞争对象不是单一炒菜机,而是厨房注意力入口**:智能屏抢的是家庭信息入口,冰箱屏抢的是食材入口,ROKI/方太抢的是厨电生态入口,炒菜机抢的是省事需求。CookMirror 应抢占的是"灶台前 30 分钟"的实时决策入口。
3. **关键差异化口号可落为一句话**:**炒菜机替你做,CookMirror 教你做、看着你做、护着你做。**
4. **商业机会在"低改造、高感知、高安全"**:相比整套数字厨电和全自动机器人厨房,CookMirror 只需壁挂安装 + 传感器/阀门接入,能兼容用户已有锅具、灶具和家庭菜谱,更适合课程 MVP 与后续量产。

### 2.2 与"全自动 AI 炒菜机"的差异化(核心质疑回应)

> ❓ 既然炒菜机能全自动做菜,为什么用户还要自己炒?

| 对比维度 | 全自动炒菜机 | CookMirror 厨魔镜 |
| --- | --- | --- |
| **产品哲学** | 替代人 | 放大人 |
| **目标心智** | 解放双手 | 享受过程 + 学会技能 |
| **价格** | ¥3000–¥100000 | ¥3999–¥5999 |
| **菜系覆盖** | 限平底/圆底标准锅腔的爆炒/红烧/炖煮 | **任意锅具、任意菜系**(蒸/煎/烤/凉拌/面食/烘焙全覆盖) |
| **复杂技法** | 颠勺、勾芡、爆炒锅气、临场调整无法做 | 人来执行,AI 实时指导火候节奏 |
| **清洁** | 内胆+搅拌叶难清洗,残留 | 不接触食物,只需擦镜面 |
| **空间占用** | 占灶台 / 大体积电器 | 壁挂式,不抢空间 |
| **学习曲线** | 用得越久越依赖 | **用得越久越会做菜**(能力沉淀) |
| **情感价值** | 工业化产物,无温度 | **保留"妈妈的味道""家的味道"** |
| **多人协作** | 单机操作 | **夫妻/亲子/远程协同**做饭 |
| **拓展性** | 单一功能 | 安全监护 + 营养 + 传承 + 社交多维拓展 |
| **多任务** | 一锅一菜串行 | **AI 调度多菜并行**(三菜一汤同时进行) |

**关键论点 1:** "做饭"对中国家庭而言是文化与情感载体,不只是供给营养。父母给孩子做饭、夫妻一起备餐、节日全家围炉,**这些过程本身就是产品价值**,不可被替代。

**关键论点 2(2025 厨房市场口径):** 更契合本项目的判断不是"智能屏比炒菜机大",而是"厨房正在换新,但家庭端自动炒菜机仍不是主流入口"。奥维云网(AVC)数据显示,2025H1 国内厨卫大电市场整体零售额 789 亿元,同比增长 3.9%;厨房小家电全渠道零售额 319 亿元,同比增长 9.3%,零售量 1.3652 亿台;刚需烟灶市场中,油烟机与燃气灶合计销量 2097 万台、销额 260 亿元。相比之下,消费级烹饪机器人公开可查的 C 端口径仍停留在 2024 年线上销量约 14 万台的早期规模;2025 年炒菜机器人热度主要来自商用餐饮后厨,行业报告预计中国炒菜机器人市场规模突破 37 亿元、约 3 万家餐厅部署。结论:CookMirror 应切入的是"家庭厨房换新 + 智能化 + 安全健康"的大盘,而不是把自己定义成小众全自动炒菜机。

数据来源:[奥维云网 AVC 2025H1 家电大盘与烟灶数据](https://finance.sina.com.cn/tech/roll/2025-07-31/doc-infikkxp2680710.shtml)、[奥维云网 AVC 2025H1 厨房小家电数据](https://article.pchome.net/content-2188204.html)、[美的集团 2025 半年度报告披露的厨卫大电/厨小电数据](https://www.podms.com/newspage.aspx?id=20250830004456)、[中国家电网 2025H1 厨电市场分析](https://news.cheaa.com/2025/0808/648584.shtml)、[奥维云网 AVC 烹饪机器人线上监测](https://finance.sina.com.cn/tech/roll/2024-08-12/doc-incimhay0998178.shtml)、[中国食品工业协会国食智库《世界炒菜机器人产业发展报告》相关报道](https://finance.sina.com.cn/roll/2025-12-18/doc-inhcetxr8687631.shtml)。

**关键论点 3:** 我们不与炒菜机竞争,而是与"用手机看菜谱"的现状竞争 ——目标用户是占 85% 的"想做菜但做不好"的家庭。

## 三、产品功能设计(创新、拓展)

### 模块 1️⃣ 烹饪指导(核心)

#### 1.0 菜谱数据库分层架构(基础)

> **关键架构决策**:CookMirror 烹饪指导**以预制菜谱为主体,AI 视觉为辅助验证,云端 API 仅兜底长尾**。不走"全 API 实时生成菜谱"路线——大模型可能瞎编步骤,可靠性达不到家用厨房标准。

| 层 | 内容 | 占比 | 实现 |
| --- | --- | --- | --- |
| 🥇 **预制菜谱**(主体) | 500 道头部菜的完整步骤序列(文字 + 图 + 视频 + 火候参数 + AI 视觉特征) | **80% 场景** | 离线访问 eMMC(详 §4.7) |
| 🥈 **AI 视觉验证**(质量层) | MobileNetV3 本地小模型(~5MB)实时确认"用户做的菜符合当前步骤" | 15% 场景 | 本地 S5P6818 推理 |
| 🥉 **云端 API**(长尾兜底) | Qwen-VL 实时识别用户自创菜 + DeepSeek 推荐菜谱组合 + 营养计算 | 5% 场景 | 仅用户授权时上云 |

**菜谱库来源(MVP 头部 500 道)**:

**端-边-云三级架构理由**:

- **S5P6818 (MPU,边缘层)**:Linux + Qt UI + AR 渲染 + 视频编码 + **WiFi/4G 通信主路径** + **麦阵语音(KWS/ASR/对话)** + 云端 API 调用
- **STM32H743 (MCU,端侧实时层)**:传感器采集 + 安全融合 + 关阀指令 + Zigbee 家电控制 + 蜂鸣 / LED / 风扇控制 + **4G 紧急接管**
- 二者通过 USART6 (500kbps + 1Hz PPS) 心跳同步;PPS 丢失 > 3s 触发 STM32 接管 4G
- **安全控制(关阀 + 报警)完全在 STM32 自治**:即使 Linux 死机、WiFi 断网,STM32 仍能本地报警 + 经紧急 4G 通道推送家属
- v2.0 修正:WiFi/4G 从 STM32 挂载移至 S5P6818(详 §4.12);**v2.1 修正:麦阵从 STM32 SAI1 改挂 S5P6818 I²S0(详 §4.5.2)**

##### MPU 选型 6 维度论证

###### ① 运算量需求

- CookMirror 边缘层任务:UI 渲染(1080p@60Hz)+ H.264 编码(1Mbps)+ MediaPipe Hands(<100MB 内存,~5ms/帧)+ KWS 唤醒词(<10MB 内存,~50ms/次)
- 实测 S5P6818 跑这些任务**总 CPU 占用 < 60%**,有余量
- 重型 AI(食材识别 / 菜谱匹配)走云端,**Mali-400 不参与 AI 推理**(详 §4.13 端云协同)
- 结论:S5P6818 算力**够边缘层用**,但**不够本地大模型**——这正是采用端云协同的根本理由

###### ② 应用领域匹配

- S5P6818 设计目标:多媒体平板 / 工业 HMI / 智能终端
- 与 CookMirror "智能镜面 + 摄像头 + 音频" 应用高度对齐
- 内置 LVDS 1080p 输出(直驱 21.5" 屏)+ MIPI-CSI 2-lane(接 OV5640)+ I²S(接音频)= 一站式覆盖外设需求

##### MCU 选型 6 维度论证

###### ① 运算量需求(MCU)

- 任务负载估算(FreeRTOS 多任务并发,**v2.1 已删除 AudioTask**):
  - SafetyTask(10ms 周期):气体阵列 ADC + 多模态融合判决,~5% CPU
  - EmergencyTask(事件触发):4G 紧急接管 + 预存 AT 命令,~3% CPU(平时 0)
  - SensorTask(50ms):I²C 轮询 8 个传感器,~3% CPU
  - ZigbeeTask(事件):CC2652R 关阀 + 家电控制,~2% CPU
  - AlarmTask(实时):蜂鸣 PWM + LED 驱动,~1% CPU
  - CommTask(20ms):USART6 与 MPU 心跳 + CRC16,~3% CPU
  - UITask + 其他:~2% CPU
  - **合计 ≈ 19% 占用,余量极充足**(原 v2.0 含 AudioTask 时 40%)
- 关键指标:**安全任务中断响应 < 1μs**(NVIC 直接进 ISR),实测 H7 @ 480MHz 完全满足
- v2.1 后 STM32 资源更宽松,可承接未来 PCB 控制 / 工业 RS485 / 第二组传感器扩展

| LTE_RI 与 I²C2_SDA (PB10) 冲突风险 | LTE_RI 改用 PE0 EXTI |
| PM2.5 ADC 与触发脉冲时序 | PA6 采样,PD14 输出定时触发,互不复用 |
| 音频/视频/主网络大流量链路占用 STM32 | 全部移至 S5P6818,USART6 只传事件和控制帧 |

### 4.5 关键电路设计要点

#### 4.5.1 关阀指令输出层(双协议,安全关键)

> **重要修正**:CookMirror **不自带燃气电磁阀**——燃气管道改装在国内属于持证作业(GB 38445-2019),不应由消费者自行施工。本产品仅作为"指令源",由用户家中**既有的智能阀 / 燃气报警联动盒**执行机械关阀动作。

**双协议关阀输出**:

| 协议 | 适用对象 | 实现路径 |
| --- | --- | --- |
| **A. Zigbee On/Off Cluster** | 智能燃气切断阀(中燃 / 港华 / 海尔 / 美埃 / Aqara) | CC2652R 发 Zigbee Cluster 0x0006 (On/Off) Off 命令 |
| **B. 12V 干接点联动输出** | 既有燃气报警联动盒(行业普遍配 12V 联动端子) | PC0 → PC817 光耦 → S8050 → 12V 继电器 → J1 接线端子 |

```text
                                                ┌── 路径 A:Zigbee 智能阀
STM32 ──► CC2652R ──► Zigbee 协议栈 ──────────►├── (中燃 / 港华 / Aqara 等)

STM32 PC0 ──► PC817 ──► S8050 ──► 12V 继电器 ──► J1 干接点
                                                  │
                                                  └── 路径 B:既有燃气报警联动盒
                                                      (12V 触发 → 盒内执行关阀)
```

**为什么不做产品自带阀**:

| 风险 | 详情 |
| --- | --- |
| **法规风险** | GB 38445-2019《建筑燃气安全检查规程》,管道改装需持证 |
| **责任风险** | 漏气/爆炸厂家承担连带责任(参考蓝芯智控 2023 案例) |
| **兼容性** | 全国燃气接口不统一(直丝/卡套/螺纹) |
| **成本** | 节省 ¥200-500/阀 + ¥50 装机,产品反而更便宜 |

**12V 输出电路仍保留**:用于路径 B(行业通用 12V 联动端子)。光耦隔离 + Fail-Safe 设计(掉电默认安全)的逻辑不变。

**已通过 Proteus §子电路 ③ 仿真验证** ✓——仿真中的"继电器吸合 → 电机转动"对应实物中的"12V 干接点导通 → 联动盒动作",电路本质不变。

#### 4.5.2 麦克风阵列布局(v2.1 改挂 S5P6818)

> **v2.1 架构修正**:麦阵从 STM32 SAI1 改挂 S5P6818 I²S0/TDM——主语音输入交给有 Linux + ALSA + 网络栈的 MPU 才合理,STM32 不承担语音任务。

**物理连接**:

- 4 颗 INMP441 等间距 30mm 直线阵列,**直出标准 I²S 接口**(无需外部 PDM 转换)
- 接 **S5P6818 的 I²S0 + TDM 4-slot** 模式(单总线 4 麦同步采样):
  - I²S_BCLK / I²S_LRCK / I²S_DATA_IN(3 根线即可)
  - 4 颗麦的 WS 引脚分时复用配置 4 个 slot(slot0-3)
- 软件层在 S5P6818 Linux 内的 ALSA 子系统统一处理

**数据流**:

```text
4×INMP441 ──I²S/TDM──► S5P6818 I²S0 ──► ALSA snd-soc ──► userspace
                                                │
                                                ├─► KWS 唤醒词检测(本地, ~10MB)
                                                ├─► 录音 + 云端 ASR(阿里云一句话识别)
                                                ├─► 油爆声 / 碎裂声 异常检测(本地小模型)
                                                ├─► GCC-PHAT 声源定位
                                                └─► 视频通话音频上行
```

**软件处理**:

- 带通滤波 80Hz-8kHz(去除工频与高频噪声)
- 波束成形(beamforming):聚焦灶台方向,抑制油烟机噪声(SNR 改善 12dB)
- 油爆声 / 碎裂声异常检测:轻量本地模型(< 5MB)→ 通过 USART6 通知 STM32
- 声源定位:GCC-PHAT 算法,辅助判断"是谁在喊'救命'"

**用途分级**:

| 用途 | 跑在哪 | 离线 |
| --- | --- | :---: |
| 唤醒词("嘿魔镜") | S5P6818 本地 KWS | ✅ |
| 自然语音对话 | 录音 → 云端 ASR + LLM + TTS | ❌ |
| 油爆 / 碎裂声异常 | S5P6818 本地小模型 → STM32 联动报警 | ✅ |
| 声源定位 | S5P6818 本地 | ✅ |
| 视频通话音频上行 | S5P6818 → ESP32 WiFi | ❌ |

**为什么不接 STM32**(v2.1 修正):

- 语音识别需要云端 ASR → 需要网络栈(S5P6818 有 Linux + ESP32 SDIO)
- KWS 模型 ~10MB → STM32 1MB SRAM 装不下
- 自然语音对话需要 LLM → 必须走云端 → MPU 调用更顺畅
- STM32 SAI1 释放 PE2-PE7,共 6 个引脚加入"预留扩展"

#### 4.5.3 摄像头与镜面光路
- 俯视摄像头嵌入烟机下沿,78° 广角覆盖整个灶台面
- 前置摄像头隐藏在镜面上方装饰条内,镜面后置不破坏外观
- 半反镜:30% 反射 + 70% 透射,LCD 关闭时纯镜面,LCD 开启时显示叠加

#### 4.5.4 防油防雾设计
- 外壳整体 IP54,镜面采用纳米疏油涂层(类似 iPhone 屏幕)
- 摄像头镜头外置加热环(类似汽车后视镜除雾),低功率防雾
- 内部主板涂三防漆(防潮防尘防腐蚀)

#### 4.5.5 电源管理
- 主路:220V AC → 12V/5A 开关电源 → 多路 DC-DC 降至 5V/3.3V
- 备用电池:2×18650 串联 7.4V,经 LDO 输出 5V,**仅供 STM32 + 报警 + 4G**(关键安全系统)
- 主 MPU 与显示在停电时关闭,延长备用电池供电至 4 小时以上

按课程 §7.1 ③ "存储器选择" 要求,本系统从工作频率、容量、位长、接口、电压五维度选型。本节同时回答关键问题:**菜谱库 / 家庭食谱传承 / 家庭成员档案 / 关阀阈值** 分别存哪里。

#### 4.7.3 关键读写策略

##### 策略 1:菜谱视频 LRU 缓存

- 默认 microSD 缓存 **100 道最常用菜的视频**(用户点击 / 系统推荐统计)
- 用户选不在本地的菜 → 边播边下(WiFi 缓冲 5s 就开播,4G 提示流量)
- 一周未播放 → 自动淘汰最久未用的
- 全量菜谱(500+ 道)在 L7 云端,按需流式

##### 策略 2:家庭食谱传承双轨

- 原视频在 microSD(用户**可拔卡到电脑备份**)
- AI 拆解步骤 + 关键帧在 eMMC(常用,低延迟离线复刻)
- 加密同步到云端(用户开启,**防 microSD 损坏丢失情感资产**)
- 默认本地优先,**云端同步需用户双重确认**(隐私敏感)

##### 策略 3:家庭成员档案三处冗余

- **eMMC** 主存(高频读,带头像照片)
- **AT24C256** 关键标识备份(过敏原 / 慢病列表的**最小化文字摘要**,防 eMMC 故障)
- **云端**(用户选择性同步,跨设备使用)

##### 策略 4:关阀阈值最严苛保护(✅ 不依赖任何高层资源)

- **STM32 内部 Flash 备份区** 主存(永远本地,**断网/MPU 死/eMMC 损坏 均仍工作**)
- **AT24C256** 备份(防 STM32 Flash 单点损坏)
- 双 CRC16 校验,启动时三选二投票

#### 4.7.4 关键选型说明

- **为什么不用 SRAM/EPROM**:SRAM 掉电丢失不适合代码区;EPROM 紫外擦除已淘汰
- **为什么用 eMMC 而非 SD 卡作系统盘**:eMMC 焊接更可靠,无接触故障,寿命管理(磨损均衡)由器件自带
- **为什么再加 E²PROM**:STM32H743 自带 Flash 擦写以扇区为单位(128KB),频繁写用户配置会快速消耗寿命;AT24C256 字节级擦写专门承接"高频小数据 + 最严苛冗余"
- **为什么 microSD 不焊死**:**家庭食谱传承的视频是用户情感资产**,必须给用户"拔卡备份"的权利;eMMC 焊死了用户拿不出来
- **为什么必须有云端 L7**:本地 microSD 30 个月就可能因 NAND 老化丢数据,云端是**家传资产的最终保险**
- **系统断电恢复**:eMMC 文件系统 ext4 带 journal;关键配置写 E²PROM 时用"原子性双 buffer"(写新 → 校验 → 切换索引)防写中断

#### 4.7.5 容量预警与扩展

- microSD 剩余 < 10% 时镜面提示用户清理或换更大卡
- eMMC 剩余 < 200MB 时强制清理 OTA 缓存

### 4.8 模拟前端与 ADC 设计

按课程 §7.1 ② "ADC/DAC" 与"模拟控制与处理电路"要求展开。

#### 4.8.1 ADC 信号链路

气体传感器是本系统唯一的模拟输入源(其他传感器均为数字接口)。

```text
   MQ-2 / MQ-5
   (输出 0-5V)
       │
       ▼
   ┌────────────┐
   │ 电阻分压网络 │  5V → 3.3V  (R1=2.2kΩ 上臂,R2=4.7kΩ 下臂)
   │ 5V→3.3V    │  分压比 = 4.7/(2.2+4.7) ≈ 0.68
   └────────────┘
       │
       ▼
   ┌────────────┐
   │ 防混叠 RC   │  一阶低通,fc ≈ 100Hz
   │ 低通滤波器  │  R=10kΩ + C=160nF
   └────────────┘
       │
       ▼
   ┌────────────┐
   │ STM32 ADC1  │  12-bit @ 480 cycles 采样
   │ PA4 / PA5   │  Vref = 3.3V(VDDA)
   └────────────┘
       │
       ▼
   软件滑动均值滤波(N=16)+ 阈值判决
```

#### 4.8.2 ADC 关键参数

| 参数 | 数值 | 依据 |
|---|---|---|
| 分辨率 | 12-bit | STM32H743 内置 ADC1 最高 16-bit,本场景气体浓度变化慢,12-bit ≈ 0.8mV/LSB 已足够 |
| 采样率 | 1Hz | 气体浓度时间常数 ~10s,Nyquist 取 2Hz 即可,1Hz 留余量 |
| 采样时间 | 480 cycles | 输入阻抗较大(分压电阻 4.7kΩ + 滤波 10kΩ),延长采样窗口确保电容充满 |
| 参考源 | VDDA = 3.3V | 用独立 LDO 供电的 VDDA 减小噪声,辅以 100nF + 4.7μF 旁路电容 |
| 转换模式 | 软件触发单次 | 低频采样,无需 DMA 连续转换,节省功耗 |

#### 4.8.3 防混叠滤波器设计

- 截止频率 fc = 1 / (2π × R × C) = 1 / (2π × 10kΩ × 160nF) ≈ **99.5Hz**
- 衰减:在 ADC 采样率 1Hz 远低于 fc,主要作用是抑制工频干扰(50Hz)与高频毛刺
- 实测:接入家用 220V 环境,工频噪声从 80mV 降至 < 5mV

#### 4.8.4 DAC 说明

本系统**不使用片上 DAC**。课程中提到的"D/A 转换器"在本设计中由 **S5P6818 I²S 数字音频接口 + MAX98357A 数字功放**承担:

- I²S 是数字音频标准接口,直接输出 PCM 数据到外部功放
- MAX98357A 内部完成 I²S 接收、DAC 与 D 类功率放大,效率 > 90%
- 比 STM32 内置 DAC(12-bit / 1Msps)音质更好,且不占 STM32 引脚

#### 4.10.4 同步电路与时钟体系

| 时钟源 | 频率 | 用途 | 精度 |
| --- | --- | --- | --- |
| HSE 外部高速晶振 | 8MHz | STM32 主时钟,经 PLL 倍频至 480MHz | ±20ppm |
| LSE 外部低速晶振 | 32.768kHz | STM32 RTC 实时时钟 (日历) | ±10ppm |
| HSI 内部高速 RC | 64MHz | 备用,主晶振故障时切换 | ±1% |
| MPU 系统时钟 | 1.4GHz | S5P6818 内部 PLL,源自 24MHz 晶振 | ±20ppm |
| 跨芯片同步 | 1Hz PPS 脉冲 | STM32 → S5P6818 时间对齐 | μs 级 |

**同步策略**:

- **复位同步**:NRST 接 **TLV803** 上电复位监控芯片,VDD 跌至 3.0V 以下立即复位,防止 brownout 状态
- **看门狗双重保险**:
  - IWDG(独立看门狗):由 32kHz 内部 LSI 驱动,即使主时钟失败仍能复位,超时 1s
  - WWDG(窗口看门狗):由 APB1 驱动,要求软件在 50ms-100ms 窗口内喂狗,防止跑飞
- **MCU-MPU 时间同步**:STM32 每秒输出一个 PPS 脉冲到 S5P6818 GPIO,Linux 内核 `pps-gpio` 模块捕获,实现 μs 级时间对齐,确保日志/事件时间戳一致
- **MPU 心跳反向监测**:MPU 收到每个 PPS 后,通过 USART6 回发 1 字节 ACK(0xA5),STM32 监听;**连续 3 秒未收到 ACK → 判定 MPU 死机 → 触发 §4.12.5 紧急接管 4G**
- **关键中断同步**:气体超阈值中断在 STM32 内部 NVIC 最高优先级,延迟 < 50ns 即可触发关阀

#### 4.11.3 若未来需要硬件加速

> 默认架构走 §4.13 端云协同方案,不需要硬件加速器。仅当面临下列场景才需要扩展硬件:

- **场景 1:用户要求完全离线运行**(数据敏感场景,如军政厨房 / 医院专用)
  - 加 **嘉楠 K230 边缘 NPU 模组**(6 TOPS,SPI/UART 挂载)
  - 本地跑 70M 参数视觉模型,精度 ≈ Qwen-VL-Max 的 80%
  - 替换 §4.13 中的云端 API 调用,其他架构保持不变
- **场景 2:视频编码瓶颈**(若 H.264 帧率不足上行)
  - 加 **Lattice CrossLink-NX 17K**(MIPI-CSI 桥接 + 编码加速)
- **场景 3:多摄像头精确同步**(扩展到双 / 多灶台监控)
  - 加 **Xilinx Spartan-7 XC7S15**(同步触发信号源)

所有加速器通过 SPI/UART 挂在 STM32 上,**不影响 §4.13 三级架构主体**。

### 4.12 WiFi (ESP32-S3) 与 4G (EC600S) 通信模块详细设计

> **架构修正 (v2.0)**:旧版把通信模组挂在 STM32 上是错误的——STM32 UART 上限 921.6kbps,装不下 H.264 视频流 (2-5Mbps),且应用层数据 99% 由 S5P6818 产生,绕道 STM32 没有意义。**新架构:WiFi/4G 主挂 S5P6818,STM32 仅保留 4G 紧急接管通道**(Fail-Safe)。

#### 4.12.1 连接拓扑与定位

```text
                  ┌── SDIO 4-bit (50Mbps) ──► ESP32-S3 ── WiFi 6/BLE5
                  │     (足以跑 H.264 1080p)
                  │
   S5P6818 ──────┤
   (MPU)         │
                  │   ┌── UART 921.6kbps ──┐
                  └───┤                     ├── 74LVC2G53 切换 ──► EC600S ── 4G
                      │   (默认 MPU 用)     │
                      │                     │
   STM32 ───────── UART 115.2kbps ──────────┘
   (MCU)            (紧急接管:MPU 死机时由 STM32 抢占)
```

| 模块 | 型号 | 主挂载 | 接口 | 角色 |
| --- | --- | --- | --- | --- |
| **WiFi 主用** | ESP32-S3-WROOM-1 | S5P6818 | SDIO 4-bit | 日常联网 + 视频通话 + BLE 配网 |
| **4G 备用 + 紧急** | 移远 EC600S-CN | S5P6818 主路径 / STM32 紧急接管 | UART (74LVC2G53 切换) | WiFi 故障切换 + 紧急报警 |

冷热备份策略(MPU 主控):

- WiFi 优先(不计流量)
- WiFi 连续 3 次心跳失败(30s) → MPU 切换 4G
- 每 5 分钟尝试回切 WiFi
- 紧急情况(MPU 死机或安全报警)→ STM32 抢占 4G,详 §4.12.5

#### 4.12.2 ESP32-S3 ↔ S5P6818 SDIO 物理连接

ESP32-S3-WROOM-1 模组在出厂固件 `ESP-AT` 或自定义固件中可作为 **SDIO 从设备**,挂在 S5P6818 的 SDMMC2 接口下。

| 信号 | 方向 | ESP32-S3 引脚 | S5P6818 引脚 | 备注 |
| --- | :---: | --- | --- | --- |
| SD_CLK | MPU→ESP | GPIO14 | SDMMC2_CLK | 50MHz,SDIO 主时钟 |
| SD_CMD | 双向 | GPIO15 | SDMMC2_CMD | 命令通道 |
| SD_DAT0 | 双向 | GPIO2 | SDMMC2_DAT0 | 数据线 0 |
| SD_DAT1 | 双向 | GPIO4 | SDMMC2_DAT1 | 数据线 1 |
| SD_DAT2 | 双向 | GPIO12 | SDMMC2_DAT2 | 数据线 2 |
| SD_DAT3 | 双向 | GPIO13 | SDMMC2_DAT3 | 数据线 3 |
| SDIO_INT | ESP→MPU | GPIO22 | GPIOB23(EXTI) | 数据就绪中断 |
| EN (使能) | MPU→ESP | EN | GPIOC8 (GPIO 输出) | 高电平工作 |
| BOOT | MPU→ESP | GPIO0 | GPIOC9 (GPIO 输出) | OTA 升级用 |
| GND | 共地 | GND | GND | **必须共地** + 完整地平面 |
| VCC_3V3 | 供电 | 3V3 | 独立 LDO AMS1117-3.3 | 500mA 峰值能力 |

**为什么用 SDIO 而非 UART**:

| 接口 | 带宽 | 跑得动 1080p H.264 (3Mbps) | 跑得动 720p 视频通话 (1.5Mbps) |
| --- | --- | :---: | :---: |
| UART 921.6kbps | 0.9 Mbps | ❌ | ❌ |
| UART 5Mbps (ESP32 极限) | 4 Mbps | 勉强 | ✅ |
| **SDIO 4-bit @ 50MHz** | **~50 Mbps** | ✅ 余量大 | ✅ |
| USB 2.0 | 480 Mbps | ✅ | ✅ |

我们选 **SDIO**——速度足够,且 S5P6818 的 SDMMC2 控制器原生支持 SDIO 模式,Linux `mmc-sdio` 子系统 + `esp-hosted-fg` 驱动可直接挂载。

**关键供电要求**:

- ESP32-S3 发射瞬间峰值电流 **≈ 500mA**,共用主 3.3V 会导致 MPU 复位
- 设计专用 LDO,输入端并联 **220μF 钽电容 + 10μF 陶瓷**,输出端 100μF + 100nF
- 模组引脚 1cm 内放 **100nF 退耦**

**天线设计要求**(PCB 布局影响):

- 模组板载 PCB 天线版本(WROOM-1)
- 天线下方 PCB **挖空区**:≥ 15mm × 35mm,不放铜、不走线
- 模组距金属物体 ≥ 15mm
- 模组距 4G 模组天线 ≥ 50mm,避免 WiFi 2.4GHz 与 LTE B40 干扰

#### 4.12.3 EC600S ↔ S5P6818 (主用) + STM32 (紧急接管)

EC600S 引脚较多(LCC 封装 42 pin),核心互联如下:

##### EC600S ↔ S5P6818(默认主路径)

| 信号 | 方向 | EC600S 引脚 | S5P6818 引脚 | 备注 |
| --- | :---: | --- | --- | --- |
| TXD | 4G→MPU | Pin 12 (UART1_TXD) | UART4_RXD | 921.6kbps |
| RXD | MPU→4G | Pin 13 (UART1_RXD) | UART4_TXD (经 74LVC2G53) | 921.6kbps |
| RTS | 4G→MPU | Pin 14 (UART1_RTS) | GPIOC10 | 硬件流控 |
| CTS | MPU→4G | Pin 11 (UART1_CTS) | GPIOC11 | |
| RESET_N | MPU→4G | Pin 26 | GPIOC12 | 低电平复位 ≥ 200ms |
| PWRKEY | MPU→4G | Pin 30 | GPIOC13 | 开/关机控制 |
| STATUS | 4G→MPU | Pin 35 | GPIOC14 | 高电平模组就绪 |
| NETLIGHT | 4G→MPU | Pin 36 | GPIOC15 | 网络状态指示 |
| RI (Ring) | 4G→双向 | Pin 39 | GPIOB24(EXTI 中断**也接 STM32**) | 短信/紧急触发,STM32 也监听 |

##### STM32 紧急接管路径

| 信号 | 方向 | STM32 引脚 | 接到哪 | 备注 |
| --- | :---: | --- | --- | --- |
| EM_UART_TX | STM32→4G | PA2 (USART2_TX 复用) | 74LVC2G53 输入 B | 紧急 UART |
| EM_UART_RX | 4G→STM32 | PA3 (USART2_RX 复用) | 74LVC2G53 输出共享 | 紧急 UART |
| LTE_SWITCH | STM32 控制 | PB8 (GPIO 输出) | 74LVC2G53 SEL 引脚 | 0=MPU,1=STM32 |
| LTE_TAKEOVER_REQ | STM32→MPU | PB9 (GPIO 输出) | S5P6818 GPIOA0(EXTI) | 通知 MPU 让出 EC600S |
| LTE_RI 监听 | 4G→STM32 | PE0 (EXTI) | EC600S Pin 39(并接) | 紧急振铃,**已避开 I²C2_SDA (PB10)** |

##### 74LVC2G53 切换电路(关键)

```text
                          74LVC2G53 (2:1 SPDT 模拟开关)
                         ┌──────────────┐
   S5P6818 UART4_TXD ────┤ A (Y0)        │
                         │              │
   STM32 PA2 ────────────┤ B (Y1)       │  COM ────► EC600S Pin 13 (UART1_RXD)
                         │              │

                         │  0: A→COM    │
                         │  1: B→COM    │
                         └──────────────┘

   (RXD 方向同理,双向切换)

   仲裁逻辑:
   ┌─────────────────────────────────────────────────────┐
   │ 默认 LTE_SWITCH=0:MPU 接通 EC600S                  │
   │                                                     │
   │ 触发紧急接管(任一条件满足):                      │
   │   - STM32 SafetyTask 检测到气体/火警 + 需上报      │

   │                                                     │
```

**关键决策**:

- **S5P6818 不跑 LwIP 协议栈**——交给 ESP32 与 EC600S 内置栈(模组厂商已过 CCC/SRRC 认证,自研栈合规风险大)
- **STM32 完全不接入主网络数据路径**,仅在紧急时使用 EC600S 的 AT 命令接口
- 视频流、家电控制、菜谱 API 等全部走 S5P6818 ↔ 模组直连

#### 4.12.5 紧急接管逻辑详解

紧急接管设计为 CookMirror 的 **Fail-Safe 灵魂**——即使 MPU 死机、Linux 卡死、WiFi 路由器失效,只要 STM32 + EC600S + 4G 网络存活,就能把"家中燃气泄漏"这种致命事件推送给家属。

##### 触发条件(STM32 任意一条满足即接管)

| 触发源 | 检测方式 | 优先级 |
| --- | --- | --- |
| 气体超阈值(MQ-2/MQ-5) | SafetyTask 10ms 周期 | 最高 |
| 空锅干烧 | MLX90640 + 红外阈值 | 高 |
| MPU 心跳超时 | MPU 对 PPS 的 ACK 丢失 > 3s | 中 |
| 物理紧急按键 | PD11 EXTI 长按 > 3s | 中 |
| 看门狗触发 | IWDG 复位标志 | 低(开机自检) |

##### 接管流程(时序约 800ms)

```text
   T=0   STM32 SafetyTask 判定需要紧急上报
         ↓
   T=10  拉高 LTE_TAKEOVER_REQ → MPU GPIOA0 中断
         ↓
   T=50  MPU 完成当前 AT 命令,释放总线,回 ACK
         ↓
   T=60  STM32 拉高 LTE_SWITCH → 74LVC2G53 切到 STM32
         ↓
   T=100 STM32 通过 PA2/PA3 发送预存 AT 序列:
         AT+QMTPUB=0,1,1,0,"alarm/cookmirror/{deviceid}","..."
         ↓
   T=500 收到 +QMTPUB: 0,1,0 回执,云端 MQTT Broker 已接收
         ↓
   T=600 STM32 通过 AT+CMGS 发短信给家属(冗余通道)
         ↓
   T=800 完成,STM32 拉低 LTE_SWITCH,归还 MPU
```

##### 预存 AT 命令模板(STM32 Flash 内固化)

```c
// 紧急 MQTT 推送 (无需 STM32 跑 TCP/IP,EC600S 内置)
const char* AT_MQTT_ALARM =
    "AT+QMTOPEN=0,\"iot.aliyun.com\",1883\r\n"      // 打开 MQTT
    "AT+QMTCONN=0,\"%s\",\"%s\",\"%s\"\r\n"          // 连接,鉴权
    "AT+QMTPUB=0,1,1,0,\"alarm/%s\",\"%s\"\r\n";     // 发布消息

// 紧急短信(冗余通道)
const char* AT_SMS_ALARM =
    "AT+CMGF=1\r\n"                                  // 文本模式
    "AT+CMGS=\"%s\"\r\n%s\x1A";                      // 发送
```

##### 与 MPU 主路径的关系

| 场景 | 谁用 4G | 切换方式 |
| --- | --- | --- |
| 日常联网 | MPU(WiFi 主用,4G 备用) | 不切换 |
| WiFi 故障 | MPU(自动切 4G) | 不切换 4G 通道,只是 MPU 内部切 |
| 安全报警 | **STM32 抢占** | LTE_SWITCH 拉高 |
| MPU 死机 | **STM32 接管** | MPU 心跳 ACK 丢失 > 3s 自动触发 |
| 报警完成 | 归还 MPU | LTE_SWITCH 拉低 |

#### 4.12.7 与端云协同的关系

WiFi 与 4G 是 **CookMirror AI 大脑的高速通道**:

- 主路径(MPU)承担 99% 流量:视频推流、菜谱 API、家电控制、AI 调用
- 紧急通道(STM32)承担 < 1% 流量但极其关键:**人命攸关的关阀报警**

两者**不可降级、不可省略**,是 CookMirror 智能体验 + 安全底线的双保险基础设施。

### 4.13 端云协同 AI 架构

> **背景**:S5P6818 (Cortex-A53 八核 + Mali-400) 是 2014 年的 SoC,实测 YOLOv8-nano 仅 3-8 FPS,本地小模型识别精度远低于 GPT-4V / Qwen-VL 等大模型。本节给出**端-边-云三级分工**的完整架构,既保证安全实时性,又最大化 AI 体验。

#### 4.13.4 隐私保护设计

| 数据类型 | 处理方式 |
| --- | --- |
| 唤醒词识别 | **完全本地**,云端永不接收原始音频 |
| 手势识别 | **完全本地**,云端不接收手部画面 |

镜面 UI 顶部状态栏实时显示当前模式:`☁️ 在线` / `📶 4G` / `📴 离线模式`。

#### 4.15.2 PCB 分板策略

整机**不放在单块板上**,分 4 块子板通过排针互联,便于单独升级:

| 子板 | 功能 | 尺寸预估 | 层数 |
| --- | --- | --- | :---: |
| **A. 主控板** | STM32H743 + 电源核心 + 时钟 + 看门狗 | 80×60mm | 4 层 (HASL) |
| **B. 传感器板** | 气体阵列 + 温湿度 + 红外 + 毫米波 + 麦阵 | 100×40mm | 2 层 |
| **C. 通信/安全板** | ESP32 + EC600S + 光耦 + 继电器 + 蜂鸣 | 80×80mm | 4 层 (含 RF) |
| **D. 显示驱动板** | LVDS 桥接 + 摄像头接口 + S5P6818 | 由实验箱提供 | — |

A/B/C 三板用 **2×10 排针** 互联,统一信号定义。

#### 4.15.3 关键 PCB 设计约束(综合 §4.12 + §4.15)

| 项目 | 规则 |
| --- | --- |
| 分区 | 数字 / 模拟 (VDDA + ADC) / RF (WiFi + 4G 天线) 三区物理隔离 + 独立地平面星形接地 |
| EMC | 开关电源附近铺地铜墙 + 过孔围栏(0.3mm 间距 1mm) |
| ESP32 天线净空 | 板载天线下方挖空 ≥ 15×35mm,不放铜不走线 |
| 4G 天线 | IPEX 接口引至板顶面,外接 LTE 棒状/弹簧天线 |
| 通信岛 | ESP32 与 EC600S 各自独立"通信岛",远离 ADC/晶振等敏感模拟区,二者间距 ≥ 50mm |
| 电源走线 | DC-DC/LDO 紧邻其供电的模组;大电容(220μF/470μF)贴近 VBAT 引脚 |
| 信号走线 | I²C 8mil 线宽;高速 UART (921.6kbps) ≤ 80mm;ADC 输入避开开关电源 ≥ 10mm |
| SIM 卡 | 距 EC600S ≤ 50mm;面板边缘开槽方便插拔 |
| 阻抗控制 | MIPI-CSI 90Ω 差分(由实验箱承担,本设计不接触) |
| 测试点 | 每个电源轨预留 1 个测试焊盘;PC0 关阀信号预留示波器探针点 |
| 认证 | ESP32/EC600S 模组已过 SRRC/CCC;整机仍需做 EMC 整改 |
